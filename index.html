Programming

$ xp --explain Disciplina de desenvolvimento de software que leva boas práticas de engenharia ao extremo: se revisar código é bom, revise o tempo todo — programação em par. Se testar é bom, teste antes de escrever o código. Se integrar é bom, integre várias vezes ao dia.

01_foco.md

Qualidade técnica e resposta rápida à mudança

XP parte de uma premissa incômoda: os requisitos vão mudar, e tentar congelá-los no início é caro. Em vez de resistir, a metodologia reduz o custo da mudança com ciclos curtíssimos, feedback constante e um código sempre limpo o bastante para ser alterado sem medo.

O eixo é a satisfação do cliente: entregar o que ele precisa, quando precisa, em vez de tudo o que ele poderia querer numa data distante. Isso se apoia em valores de comportamento, não em documentação — e exige muita disciplina. É indicada especialmente para times pequenos e médios diante de requisitos voláteis.

// os cinco valores

Comunicação

Conversa direta entre cliente, programadores e gestão substitui a documentação formal como forma de espalhar conhecimento.

Simplicidade

Fazer a coisa mais simples que possa funcionar. Projetar para hoje, não para um futuro incerto.

Feedback

Do sistema pelos testes, do cliente pelas entregas, do time pelas estimativas. Rápido e frequente.

Coragem

Para refatorar código que funciona, jogar fora o que não serve e dizer "não" quando for verdade.

Respeito

Ninguém quebra a build nem atrasa o colega. Todos contribuem e são valorizados.acrescentado na 2ª ed., 2004

// as quatro atividades básicas e os princípios

  • codificar()O único produto indispensável. Código também comunica: quando explicar é difícil, escreve-se o código para mostrar a ideia.
  • testar()Se um pouco de teste elimina alguns defeitos, muito teste elimina muitos. Não é fase, é atividade permanente.
  • ouvir()Programadores precisam entender o negócio o bastante para devolver feedback técnico sobre o que é viável.
  • projetar()Sem projeto o sistema vira um emaranhado de dependências. Com projeto simples e contínuo, mudar uma parte não quebra as outras.
  • feedback rápidoQuanto menor o intervalo entre a ação e o retorno, mais rápido o time aprende e corrige.
  • assumir simplicidadeTratar todo problema como se a solução fosse simples. Recusar o "codificar para reúso futuro".
  • mudança incrementalMuitas mudanças pequenas funcionam melhor do que uma grande de uma vez.
  • abraçar a mudançaRequisito que virou do avesso não é problema: é informação para a próxima iteração.
  • trabalho de qualidadeNinguém gosta de fazer trabalho ruim. Qualidade não é a variável que se negocia.

As práticas são interdependentes: cada uma cobre o ponto fraco das outras. É por isso que Stephens e Rosenberg argumentam que adotar só uma parte delas tende a derrubar o processo inteiro.

// vermelho, verde, refatorar — o ciclo do TDD

1 · vermelho
// história: calcular salário líquido $ sunit run SalarioTest FAIL testDescontaINSS 1 teste, 1 falha

Escreve-se o teste antes do código. Ele falha porque a funcionalidade ainda não existe — e o teste vira a definição de "pronto".

2 · verde
$ sunit run SalarioTest PASS testDescontaINSS 1 teste, 0 falhas // código feio, mas passando

Escreve-se o código mais simples que faz o teste passar, e nada além disso. É o YAGNI na prática.

3 · refatorar
~ tabela do INSS extraída p/ classe $ sunit run SalarioTest PASS testDescontaINSS comportamento externo intacto

Com o teste verde, melhorar a estrutura interna é seguro: se algo quebrar, o teste avisa na hora.

02_origem.log

Kent Beck, na folha de pagamento da Chrysler

A Chrysler contratou Kent Beck, um nome forte em Smalltalk, para fazer ajuste de desempenho no sistema C3 (Chrysler Comprehensive Compensation System). Ao entrar no projeto ele viu problemas no processo, não só no código: propôs girar até 10 os botões das práticas que considerava essenciais e desligar o resto. Beck assumiu a liderança do C3 em março de 1996; o site oficial registra 6 de março de 1996 como início do primeiro projeto XP.

CriadorKent Beck

Formulou e nomeou a metodologia no C3, escreveu o livro fundador e depois consolidou o TDD como prática difundida.

Influência decisivaWard Cunningham

Colaborador frequente de Beck; muitas ideias vieram do trabalho conjunto dos dois. Seu WikiWikiWeb foi onde o XP se difundiu.

Coach do primeiro timeRon Jeffries

Convidado por Beck para o C3, atuou como coach transformando as práticas em hábito na equipe.

Documentação das regrasDon Wells

Publicou em 1999 as 29 regras de XP no extremeprogramming.org, hoje a referência canônica online.

03_ciclo-de-vida.md

Seis fases, do primeiro cartão até a morte

Beck descreve o ciclo de vida de um projeto XP ideal no capítulo 21 do livro. Não é uma cascata: as fases se sobrepõem e o coração do processo é o laço de iteração, que se repete continuamente da terceira fase em diante.

1

Exploraçãoexploration

O cliente escreve as primeiras histórias; o time experimenta a tecnologia, testa a arquitetura com spikes e aprende a estimar. Termina quando as histórias são suficientes para uma primeira release.

sai daqui: primeiras histórias · spikes de arquitetura · metáfora do sistema

2

Planejamentoplanning

O jogo do planejamento: cliente prioriza, programadores estimam. Define-se o conjunto menor de histórias com mais valor de negócio e a data da primeira release. Costuma levar poucos dias.

sai daqui: plano de release · data da primeira entrega

3

Iterações até a primeira releaseiterations to release

Série de iterações curtas, de 1 a 3 semanas, produzindo software testado e funcionando. A primeira iteração normalmente monta o esqueleto da arquitetura; as demais entregam histórias priorizadas.

sai daqui: plano de iteração · testes · software funcionando · velocidade medida

4

Produçãoproductionizing

Testes mais rigorosos, ajuste de desempenho e validação antes de o sistema entrar em operação real. As iterações podem encurtar. Ideias novas não entram no meio: viram histórias para depois.

sai daqui: sistema em produção · histórias adiadas para a próxima release

5

Manutençãomaintenance

Estado normal de um projeto XP. Desenvolver novas funcionalidades enquanto se mantém o sistema em produção. A velocidade tende a cair e o time pode mudar de composição.

sai daqui: novas releases · suporte ao sistema vivo

6

Mortedeath

Quando o cliente não tem mais histórias a escrever e o sistema atende às necessidades — ou quando o custo de mantê-lo deixa de compensar. É a hora da documentação final do sistema.

sai daqui: documentação final do sistema

04_artefatos.md

Cartões, testes e código que funciona

XP produz poucos artefatos, e quase todos são leves e descartáveis. Os requisitos vivem em cartões de história, não em especificações; os testes automatizados substituem boa parte da documentação; e o entregável real é sempre software rodando.

Requisito

Histórias do usuário

Cartões curtos escritos pelo cliente descrevendo uma funcionalidade em linguagem de negócio. Base para estimativa e priorização.

Planejamento

Plano de release

Quais histórias entram em qual versão e quando. É o resultado do jogo do planejamento.

Planejamento

Plano de iteração

Histórias selecionadas para o ciclo atual, quebradas em tarefas assumidas pelos próprios programadores.

Execução

Cartões de tarefa

Unidades técnicas derivadas das histórias, estimadas em horas ideais por quem vai implementar.

Projeto

Cartões CRC

Classe, responsabilidade e colaboração. Usados em sessões rápidas de projeto coletivo, sem UML pesada.

Projeto

Spike solutions

Protótipos descartáveis feitos só para reduzir risco técnico e melhorar uma estimativa. O código é jogado fora depois.

Qualidade

Testes unitários

Automatizados e escritos antes do código. Todo o código precisa passar em 100% deles para ser liberado.

Qualidade

Testes de aceitação

Definidos pelo cliente a partir das histórias. Executados com frequência e com o placar publicado ao time.

Métrica

Velocidade do projeto

Quanto trabalho o time entregou na iteração anterior. É o único insumo para planejar a próxima.

Comunicação

Metáfora do sistema

Uma história ou nome comum que dá ao time um vocabulário compartilhado sobre como o sistema funciona.

Convenção

Padrão de codificação

Acordado por todos. Viabiliza a propriedade coletiva do código e o rodízio de duplas.

Entrega

Pequenas versões

Software funcionando entregue ao cliente ao fim de cada iteração. É o artefato que realmente importa.

XP minimiza documentação formal: o código legível, os testes automatizados e a conversa presencial são a documentação viva do projeto. A documentação final do sistema é escrita na fase de morte.

05_papeis.md

Sete papéis, um time só

Beck define os papéis no capítulo 22 do livro. Não são cargos hierárquicos: gerentes, clientes e desenvolvedores são parceiros iguais num time colaborativo que se auto-organiza em torno do problema.

Programadorprogrammer

O papel central. Escreve testes e código, sempre em par, mantém o projeto o mais simples possível, refatora sem pedir licença e se comunica constantemente com colegas e cliente.

Clientecustomer

Escreve as histórias e os testes de aceitação, define prioridades e decide o escopo de cada release. Precisa estar disponível ao time o tempo todo — a prática do on-site customer.

Testadortester

Ajuda o cliente a escolher e escrever os testes de aceitação, executa-os regularmente, divulga os resultados e mantém as ferramentas de teste funcionando.

Rastreadortracker

A consciência do time. Mede a velocidade do projeto, compara estimativas com o realizado e devolve esse retrato à equipe para que as próximas estimativas melhorem.

Treinadorcoach

Guardião do processo. Percebe quando o time está se desviando das práticas, ensina, sugere ajustes e mantém a calma quando o projeto aperta.

Consultorconsultant

Especialista externo acionado pontualmente para um problema técnico específico. Ensina o time a resolver, em vez de resolver no lugar dele.

Gerentebig boss

Garante recursos, ambiente de trabalho aberto e confiança. Cobra resultados sem microgerenciar e dá ao time a coragem para seguir o processo.

Na 2ª edição (2004) Beck amplia a lista com papéis como arquiteto, designer de interação, gerente de produto, redator técnico, usuário e executivo — e ressalva que, num time maduro, os papéis não são fixos nem rígidos: o objetivo não é preencher funções abstratas, e sim que cada pessoa contribua com tudo o que puder.

06_regras.cfg

As 29 regras oficiais, em cinco categorias

As 12 práticas são a versão mais divulgada do XP, mas a documentação de Don Wells organiza o método em 29 regras. Planejamento, gerenciamento e projeto aparecem explicitamente para rebater a acusação de que o XP "não planeja e não projeta".

planejamento/ 5

  1. Histórias do usuário são escritas.
  2. O planejamento de release cria o cronograma de entregas.
  3. Faça pequenas versões com frequência.
  4. O projeto é dividido em iterações.
  5. O planejamento da iteração inicia cada iteração.

gerenciamento/ 6

  1. Dê ao time um espaço de trabalho aberto e dedicado.
  2. Estabeleça um ritmo sustentável.
  3. Uma reunião em pé inicia cada dia.
  4. A velocidade do projeto é medida.
  5. Faça rodízio de pessoas entre as duplas.
  6. Conserte o XP quando ele quebrar.

projeto/ 6

  1. Simplicidade.
  2. Escolha uma metáfora do sistema.
  3. Use cartões CRC nas sessões de projeto.
  4. Crie spike solutions para reduzir risco.
  5. Nenhuma funcionalidade é adicionada antes da hora.
  6. Refatore sempre e onde for possível.

codificacao/ 8

  1. O cliente está sempre disponível.
  2. O código segue o padrão acordado.
  3. Escreva o teste unitário primeiro.
  4. Todo código de produção é feito em dupla.
  5. Só uma dupla integra código por vez.
  6. Integre com frequência.
  7. Mantenha um computador dedicado à integração.
  8. Adote propriedade coletiva do código.

testes/ 4

  1. Todo código precisa ter testes unitários.
  2. Todo código precisa passar em todos os testes antes de ser liberado.
  3. Quando um bug é encontrado, criam-se testes para ele.
  4. Os testes de aceitação rodam com frequência e o placar é publicado.
07_critica.md

Vantagens, limitações e críticas

O XP é uma das metodologias mais debatidas da engenharia de software. Apresentar os dois lados costuma valer mais do que vender o método — é o que diferencia um trabalho descritivo de um trabalho crítico.

// pass

O que o XP entrega bem

  • Reduz o custo da mudança: mudar um requisito na iteração 7 custa quase o mesmo que na iteração 2.
  • Defeitos aparecem cedo, quando ainda são baratos de corrigir.
  • Conhecimento distribuído pelo time — par, rodízio e propriedade coletiva reduzem a dependência de pessoas-chave.
  • O cliente vê valor real a cada iteração, em vez de esperar meses por uma entrega única.
  • Menos desperdício: só se implementa o que foi priorizado, evitando funcionalidades que nunca serão usadas.
  • O código permanece íntegro: refatoração contínua e cobertura de testes evitam a degradação típica de sistemas longos.

// fail

Onde ele falha ou é contestado

  • As práticas são interdependentes — Stephens e Rosenberg argumentam que, como poucas organizações adotam todas, o processo inteiro tende a falhar.
  • Exige disciplina alta e constante; sem ela, o XP vira improviso com nome bonito.
  • Sem controle formal de mudanças, o escopo pode crescer além do contratado.
  • O cliente disponível em tempo integral é um ponto único de falha, é caro e pode virar fonte de estresse.
  • A ausência de especificação de projeto dificulta auditoria, contratos de preço fechado e a entrada de novos times.
  • Par, rodízio e refatoração mal aplicados podem, de fato, aumentar custo e prazo.
  • Não escala naturalmente: Beck reconhece que o XP funciona mal em times grandes. O IXP (Industrial XP, 2004) surgiu como tentativa de adaptação, com 23 práticas.
08_xp-vs-scrum.md

XP e Scrum lado a lado

A comparação mais provável de aparecer numa pergunta. A diferença essencial: o Scrum organiza como o trabalho flui e é silencioso sobre engenharia; o XP prescreve como se programa. Por isso os dois são frequentemente combinados, e não escolhidos um em vez do outro.

Extreme ProgrammingScrum
FocoPráticas técnicas de engenhariaGestão e fluxo do trabalho
CicloIteração de 1 a 3 semanasSprint de 1 a 4 semanas
PapéisProgramador, cliente, testador, rastreador, treinador, consultor e gerenteProduct Owner, Scrum Master e time de desenvolvimento
Quem priorizaO cliente, presente no time em tempo integralO Product Owner, via backlog do produto
Mudança no meio do cicloAceita, desde que uma história equivalente saia do lugarEscopo da sprint protegido depois do planejamento
Prescreve como programarSim: TDD, par, integração contínua, refatoração, padrão de códigoNão: cada time decide suas práticas técnicas
ArtefatosHistórias, plano de release, plano de iteração, cartões CRC, testes automatizadosProduct Backlog, Sprint Backlog e Incremento
Na práticaCombinação comum: Scrum para organizar o fluxo e as cerimônias, XP para garantir a qualidade técnica dentro dele.
09_glossario.md

Glossário

Os termos que você precisa saber explicar sem ler o slide.

História do usuáriouser story
Descrição curta de uma funcionalidade, escrita pelo cliente em linguagem de negócio, num cartão. Não é uma especificação: é uma promessa de conversa.
Jogo do planejamentoplanning game
Reunião em que o cliente prioriza histórias por valor de negócio e os programadores estimam esforço. Ninguém invade o papel do outro.
Velocidade do projetoproject velocity
Quantidade de trabalho concluída na iteração anterior. É o único insumo para prever quanto cabe na próxima: planejamento empírico, não especulativo.
Spikespike solution
Protótipo descartável, com prazo curto, feito só para responder a uma dúvida técnica e melhorar uma estimativa. O código é jogado fora depois.
Metáfora do sistemasystem metaphor
Uma imagem ou nome compartilhado que dá ao time um vocabulário comum sobre como o sistema funciona, substituindo o jargão de arquitetura.
TDDtest driven development
Escrever o teste que falha antes do código que o faz passar. Inverte a ordem tradicional e transforma o teste em especificação executável.
Refatoraçãorefactoring
Melhorar a estrutura interna do código sem alterar seu comportamento externo. Feita continuamente, não como projeto separado.
Propriedade coletivacollective ownership
Qualquer dupla pode alterar qualquer arquivo, sem pedir autorização. Sustentada pelo padrão de código, pelos testes e pelo rodízio.
Integração contínuacontinuous integration
Integrar o código várias vezes ao dia, rodando toda a bateria de testes. Nada entra se algum teste falhar.
YAGNIyou aren't gonna need it
"Você não vai precisar disso." Regra contra implementar hoje o que só talvez seja útil amanhã.
Reunião em péstand-up meeting
Encontro diário curto, feito de pé justamente para não se estender, sobre o que foi feito, o que será feito e quais os impedimentos.
Ritmo sustentávelsustainable pace
Antes chamado de "semana de 40 horas". Hora extra crônica derruba a qualidade e a velocidade: cansaço produz defeito.
Cartão CRCclass-responsibility-collaboration
Cartão com o nome de uma classe, o que ela faz e com quem colabora. Ferramenta de projeto coletivo em mesa, sem UML pesada.
Teste de aceitaçãoacceptance test
Teste definido pelo cliente a partir de uma história. Determina se a funcionalidade está pronta do ponto de vista do negócio.
